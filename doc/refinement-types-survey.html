§ 2

The VC-Generation-and-Discharge Story

Refinement type systems reduce type-checking to a sequence of implication queries over a fixed decidable logic. Each query is generated once, statically, at the point where a value must inhabit a refined type. No runtime checks are emitted. The architecture has four layers.

Layer 1 — Refinement types as predicate-indexed sets

A refinement type {ν:B | p(ν)} denotes the set {v | v : B ∧ p[v/ν]}. The base type B is a simple type (Int, Bool, …); the predicate p is drawn from a fixed decidable logic L. The key invariant: p is never a term of the object language — it lives in a separate index or qualifier language, which is what makes the whole system decidable.

In Liquid Types / LiquidHaskell [1,2], L is QF-UFLIA — the quantifier-free fragment of linear integer arithmetic extended with uninterpreted functions (for polymorphism). In DML [3], L is Presburger arithmetic (linear integer arithmetic with quantifiers, decided by Cooper's algorithm / the Omega test). In F* [4], L is Z3's full logic (technically undecidable, but pure-fragment arithmetic goals are handled automatically).

Layer 2 — Subtyping = implication (the Sub-Base rule)

The only rule that generates a proof obligation is the subtype check. All other typing rules are structural. From Jhala & Vazou [2,tutorial], the core rule is:

Sub-Base
Γ ⊢ ∀ν₁:b.  p₁  ⇒  p₂[ν₂:=ν₁]

Γ ⊢ b{ν₁:p₁}  ≺:  b{ν₂:p₂}

The environment Γ = x₁:T₁,…,xₙ:Tₙ where each Tᵢ = bᵢ{ν:qᵢ}. Each binding xᵢ:{bᵢ|qᵢ} contributes the ground fact qᵢ[xᵢ/ν] — that is, "I know qᵢ(xᵢ) holds" — as a hypothesis.

The SMT query sent for Sub-Base is therefore the closed formula: 

Valid(  (⋀ᵢ qᵢ(xᵢ))  ∧  p₁(ν)  ⟹  p₂(ν)  )

This is a quantifier-free formula in the decidable fragment L. The SMT solver returns Valid/Invalid in a single call. If valid, no runtime check is emitted. If invalid, the program is rejected at type-check time.

Layer 3 — VC shape per expression form

Every expression either synthesizes a type or is checked against an expected type. A check triggers Sub-Base when the synthesized type and expected type differ. The table below shows the obligations for the most important expression forms:

Expression form VC generated Hypothesis from Γ needed
x - y : {v|v ≥ 0} Γ ⊢ (v = x − y) ⟹ (v ≥ 0) y ≤ x (from branch guard)
a[i] : {v|v = a[i]} Γ ⊢ 0 ≤ i ∧ i < len(a) Bounds previously established
f (e : T₁) : T₂ Γ ⊢ synth(e) ≺: T₁ (precondition sub-check) Context facts about e's components
let x = e₁ in e₂ : T x:synth(e₁) added to Γ; check e₂ : T in Γ′ Γ′ now includes facts about x
fun (x:T₁) → e : T₁→T₂ x:T₁ added to Γ; check e : T₂ in Γ′ Refinement of argument type

§ 3

How a Runtime Guard Becomes a Static Hypothesis

This is the mechanism the user's question most directly asks about. The answer is precise and uniform across all systems surveyed: the branch condition is syntactically added to the typing environment for the relevant branch, where it contributes as a ground fact to every Sub-Base query generated inside that branch.

The Chk-If rule (Liquid Types / LiquidHaskell)

From Jhala & Vazou [tutorial, §chk-if]:

Chk-If
y fresh    Γ ⊢ x ⇐ bool
Γ; y:{Int | x}  ⊢ e₁ ⇐ t
Γ; y:{Int | ¬x} ⊢ e₂ ⇐ t

Γ ⊢  if x then e₁ else e₂  ⇐ t

The guard x : bool is added to the then-branch environment as a fresh binding y:{Int | x} — that is, a new fact encoding "the condition x holds." In the else-branch, the negation y:{Int | ¬x} is added instead. From that point, every Sub-Base query inside e₁ has x as a ground hypothesis.

The key point: the branch condition is not a runtime assertion or a dynamic check — it is a static enrichment of the typing context. The SMT solver sees it as an additional antecedent in the implication, not as something to be evaluated at runtime.

Worked example — safe subtraction

Consider a function that subtracts y from x and promises the result is non-negative: 

safe_sub : x:Int → y:Int → {v:Int | v ≥ 0}
safe_sub x y =
  if y <= x then x - y else 0

The type-checker processes the then-branch x - y in the environment: 

Γ′ = { x : Int,
        y : Int,
        guard : {Int | y ≤ x} }   -- added by Chk-If

The synthesized type of x - y is {v:Int | v = x - y}. The expected return type is {v:Int | v ≥ 0}. Sub-Base generates the VC: 

Valid( y ≤ x  ∧  v = x − y  ⟹  v ≥ 0 )

This is a valid QF_LIA formula. Z3 discharges it in microseconds. The result: no runtime check for v ≥ 0 is emitted. The program is verified once, completely, at type-check time.

The DML variant — index constraints

DML [3] uses a distinct but equivalent mechanism. Types are parameterized by index expressions: 'a list(n) asserts the list has length n. The type-checker generates index constraints; a branch guard if y <= x adds the Presburger constraint y ≤ x to the constraint accumulator for the true branch. Type-checking reduces to deciding satisfiability in Presburger arithmetic — decidable by the Omega test, no SMT solver required.

The critical design point (Xi & Pfenning): the index domain is completely disjoint from the term domain. Index variables are compile-time quantities; they have no runtime representation. The phase distinction is total: constraint-checking is pure static analysis.

The F* / WP calculus variant

F* [4] uses a weakest-precondition calculus rather than typing-rule subtyping. For conditionals, the WP transformer is (from the F* tutorial): 

WP(if e then e₁ else e₂, Q) =
  (e ⟹ WP(e₁, Q))  ∧  (¬e ⟹ WP(e₂, Q))

The guard e appears as a logical assumption inside each branch's WP computation. For if (y <= x) then x - y with postcondition Q ≜ v ≥ 0: 

WP = (y ≤ x ⟹ (x − y ≥ 0))  ∧  (¬(y ≤ x) ⟹ ...)
   = (y ≤ x ⟹ x − y ≥ 0)  ∧  (x < y ⟹ ...)

The obligation (y ≤ x ⟹ x − y ≥ 0) is valid in linear arithmetic; Z3 discharges it. The Dafny system works identically through Boogie as an intermediate verification language — the guard becomes an assume(y ≤ x) in the then-branch's Boogie encoding.

§ 4

Metatheory — How Preservation Is Stated and Proved

The standard syntactic approach

In Liquid Types [1] and DML [3], soundness is proved via the twin properties of progress and preservation (subject reduction):

  • Progress: If Γ ⊢ e : T and e is a closed expression, then e is a value or e → e′.
  • Preservation: If Γ ⊢ e : T and e → e′, then Γ ⊢ e′ : T.

The preservation proof proceeds by induction on the reduction derivation. The essential lemma is type substitution: if Γ, x:{B|p} ⊢ e : T and v is a value with Γ ⊢ v : {B|p}, then Γ ⊢ e[v/x] : T[v/x]. This holds because substituting a concrete refined value for a refined variable preserves the SMT validity of all Sub-Base constraints — the hypotheses in Γ grow stronger, not weaker.

The Jhala-Vazou tutorial [tutorial] states the soundness result as three propositions linking the constraint generation algorithm to the typing judgment:

Soundness (propositions 3.4.1–3.4.3)
If sub(s, t) = c   and  Γ ⊢ c,   then  Γ ⊢ s ≺: t
If synth(Γ, e) = (c, t)  and  Γ ⊢ c,   then  Γ ⊢ e ⇒ t
If check(Γ, e, t) = c   and  Γ ⊢ c,   then  Γ ⊢ e ⇐ t

In words: if the constraint generated by the algorithm is provable (i.e., the SMT solver succeeds), then the corresponding typing judgment holds. Soundness of the system then follows from the soundness of the SMT solver for the decidable logic fragment L.

The semantic approach and its difficulty

Practical refinement type systems use semantic subtyping: subtyping is not defined syntactically but through set inclusion of denotations. The denotation of a refinement type is: 

⟦ {ν:B | p} ⟧  =  { v  |  v : B  ∧  p[v/ν] = true }

Semantic subtyping: T₁ ≺: T₂ holds iff ⟦T₁⟧ ⊆ ⟦T₂⟧. For base types this collapses to the implication ∀ν. p₁(ν) ⟹ p₂(ν), which is why Sub-Base works. The difficulty arises when combining semantic subtyping with parametric polymorphism: a type variable α may be instantiated with any refined type, so the denotation of a polymorphic type mentions denotations of type arguments, which may themselves be refinements — creating a potential circularity.

Borkowski, Vazou & Jhala, POPL 2024 [6] solve this by presenting λRF, the first core calculus to combine semantic subtyping and parametric polymorphism with a mechanized metatheory. Their solution:

  • The refinement predicates live in a decidable first-order theory L, completely separated from the term language. Their truth-values are determined by an oracle (the SMT solver) without reference to the semantics of the host language. This eliminates the circularity.
  • They introduce data propositions — a novel feature encoding derivation trees for inductively defined judgments as refined data types — enabling the metatheory to be expressed and checked within LiquidHaskell itself.

The main soundness theorem of λRF:

Semantic Soundness (Borkowski, Vazou, Jhala 2024)
If  Γ ⊢ e : T  is derivable, then
for all substitutions θ satisfying Γ —
  i.e., θ(xᵢ) ∈ ⟦Tᵢ⟧ for all xᵢ:Tᵢ ∈ Γ —
we have  θ(e) ∈ ⟦T⟧.

This is stronger than syntactic preservation: it says every well-typed closed term, when it reduces to a value, reduces to a value in the denotation of its type. Progress and preservation follow as corollaries.

DML preservation specifics

In DML [3], preservation is simpler because the index domain is provably separate from the term domain. Subject reduction holds by induction on reduction derivations; the key lemma is the index substitution lemma: if Γ; Φ ⊢ e : T(i) and the constraint Φ entails i = j, then Γ; Φ ⊢ e : T(j). Index variables are compile-time quantities — they are erased before execution — so reduction preserves the structural (erased) ML type, and the index satisfies its constraint by the solver's soundness.

Base case vs. inductive step

To be explicit about the proof structure for preservation in the syntactic approach:

  1. 1
    Base case — values. A value v has type {ν:B | p} iff p[v/ν] = true. This is established at the point of type-checking and does not change — values do not reduce further, so preservation holds trivially.
  2. 2
    Inductive step — beta reduction. For (λx:T₁.e) v → e[v/x]: by the typing rule for application, we have Γ ⊢ v : T₁ and Γ, x:T₁ ⊢ e : T₂. By the substitution lemma, Γ ⊢ e[v/x] : T₂[v/x]. Since v is a value satisfying the refinement in T₁, all Sub-Base constraints involving x remain valid under the substitution — the SMT solver saw them at type-check time, not runtime.
  3. 3
    Inductive step — contextual reduction. For a term e in an evaluation context E[e] → E[e′]: the typing derivation for E[e] has a sub-derivation for e. By the inductive hypothesis, e′ has the same type as e. Plugging back into the context typing rule recovers the full typing of E[e′].
The crucial observation: Refinement predicates are not loop invariants that must hold at every intermediate step. They are entry contracts — the type system verifies that whenever a value is placed into a refined type context, it satisfies the predicate. The static discharge (via SMT) is the proof, done once. The operational semantics never needs to re-evaluate the predicate.

§ 5

Connecting to Your Problem — Rationals ≥ 0

Your formulation: "a computed rational value must stay ≥ 0, enforced as a statically-checked refinement." The survey above gives you the exact machinery:

  1. 1
    Type: {v:Q | v ≥ 0} — a refinement of the rational base type with a linear arithmetic predicate. This lives in QF_LIA (over Q or Z, both are Presburger-decidable).
  2. 2
    Operation (subtraction): typing x - y : {v:Q | v ≥ 0} generates the VC Valid(hyps ∧ v = x − y ⟹ v ≥ 0). The hypothesis y ≤ x must be in Γ for this to be discharged.
  3. 3
    Guard: if (y ≤ x) then x - y — the Chk-If rule adds y ≤ x to Γ for the then-branch. The VC is now dischargeable.
  4. 4
    Preservation: Once the SMT solver discharges the VC at type-check time, the result carries type {v:Q | v ≥ 0} everywhere it is used downstream. Subsequent operations on it inherit the hypothesis v ≥ 0 in Γ via their own binding.

For a POPL paper, the theoretical contribution would be: specifying the refinement logic L (Presburger arithmetic over Q, or your custom grade algebra), defining the Sub-Base rule, proving the substitution lemma, and invoking the soundness of the SMT solver for L. The Borkowski-Vazou-Jhala framework [6] provides the metatheoretic template.
