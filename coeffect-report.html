Research Report · Type Theory

Structural vs Flat Coeffects in Petricek, Orchard & Mycroft

Covers ICALP 2013 — "Coeffects: Unified static analysis of context-dependence" — and ICFP 2014 — "Coeffects: A calculus of context-dependent computation."
Annotated: exact = direct quote or formula confirmed from primary source; reconstructed = reconstructed from multiple corroborating secondary sources.

§1

What Coeffects Are

"Monadic effect systems provide a unified way of tracking effects of computations, but there is no unified mechanism for tracking how computations rely on the environment." — Petricek, Orchard, Mycroft exact [ICALP 2013]
"Effects capture how computations affect the environment, coeffects capture the requirements that computations place on the environment." — Petricek et al. exact [tomasp.net/coeffects]

Both papers use a single typed judgment form annotated with coeffect information. The key difference between flat and structural coeffects is the shape of that annotation: one scalar for the whole context (flat), or a per-variable vector (structural).

§2

Flat Coeffects — Whole-Context Annotation

A flat coeffect system attaches one annotation r to the entire typing context. The judgment reads:

x₁:τ₁, …, xₙ:τₙ @ r ⊢ e : τ ────────────────────────────────────────────────────────── r ∈ (L, ⊔, ⊓, ⊥, ⊤) — a bounded semilattice

What r means: the single annotation describes a property of the entire execution environment that e requires — not of any individual variable. All variables in scope share the same context demand.

How Annotations Combine

In the flat system three combining operators are needed reconstructed:

⊔ (join / merge)
Used in the application rule: if the function needs r₁ and the argument needs r₂, the result needs r₁ ⊔ r₂. Least upper bound — "either requirement must be met."
⊓ (meet / split in lambda)
Used in the abstraction rule: separates what the function needs at definition-time from what it will need at call-time. The meet r₁ ⊓ r₂ picks the greatest common requirement.
⊙ (sequential composition)
Combines a function's coeffect with its argument's when a call is made; concrete instantiation varies by analysis.

Concrete Instantiation — Implicit Parameters

The annotation r is a set of implicit parameter names. Context is required to supply exactly those names.

Carrier: 𝒫(Names) (powerset) ⊔ = ∪ (union — LUB in the subset lattice) ⊓ = ∩ (intersection — GLB) ⊥ = ∅ (no parameters needed) ⊤ = Names (all parameters needed) Example: ⊢ use ?x + use ?y @ {x, y} : Int
"The flat system for tracking [implicit parameters] is an instance of the same coeffect calculus as the one for tracking caching requirements for dataflow programs." — summarised from Petricek et al. 2013 exact paraphrase [interactive tutorial]

Concrete Instantiation — Dataflow (Limited Precision)

The annotation r is a natural number: the maximum number of past values any variable in scope needs.

Carrier: ℕ ∪ {∞} (bounded natural numbers) ⊔ = max (LUB — "need at least this many past values") ⊓ = min (GLB — used in lambda rule) ⊙ = + (sequential: prev∘prev needs 2) ⊥ = 0 Example: ⊢ (x + prev y) / 2 @ 1 : Num (one past value needed — but only by y; flat loses the per-variable precision)
The flat precision problem: for x + prev y, the flat system reports annotation 1 for the whole context, losing the insight that only y needs history. Structural coeffects fix this.

§3

Structural Coeffects — Per-Variable Annotation

"We develop a generalized coeffect system with annotations indexed by a coeffect shape. By instantiating a concrete shape, our system captures previously studied flat (whole-context) coeffects, as well as structural (per-variable) coeffects." — Petricek, Orchard, Mycroft exact [ICFP 2014]

In a structural system, every variable in the context carries its own annotation. The judgment becomes a vector:

x₁:τ₁ @ r₁, …, xₙ:τₙ @ rₙ ⊢ e : τ equivalently written Γ ⊢ e : τ where Γ maps each xᵢ to (τᵢ, rᵢ) rᵢ ∈ (R, ⊕, ⊗, 0, 1) — a (pre-ordered) semiring

The Semiring — Exact Structure

The semiring (R, ⊕, ⊗, 0, 1) used for structural annotations reconstructed from multiple sources:

⊕ (addition)
Combines requirements from parallel/choice branches. If two branches need r and s of the same variable, the outer context needs r ⊕ s. Commutative and associative; 0 is identity.
⊗ (multiplication / tensor)
Combines requirements sequentially: applying a function that needs r of variable x to an argument needing s of x yields r ⊗ s. Also used in the application rule to multiply the function's annotation with the argument's annotation element-wise. 1 is identity.
0 (zero)
"Variable not used." Annotation of any variable absent from the expression.
1 (one)
"Variable used exactly once / in the default way." The annotation given to the variable in the var rule; all other variables get 0.

Key Typing Rules (Structural)

VAR (structural) ───────────────────────────────────────────────────────── x₁:τ₁@0, …, xᵢ:τᵢ@1, …, xₙ:τₙ@0 ⊢ xᵢ : τᵢ ABS (structural) Γ, x:τ@r ⊢ e : τ′ ──────────────────────────────────────────────────── Γ ⊢ λx.e : τ —[r]→ τ′ (r is the demand on x) APP (structural) Γ₁ ⊢ f : τ —[r]→ τ′ Γ₂ ⊢ a : τ ──────────────────────────────────────────────────── Γ₁ ⊗ Γ₂ (plus r·Γ₂) ⊢ f a : τ′ (context combination: pointwise ⊗ of annotation vectors)
The "coeffect-annotated function type" τ —[r]→ τ′ records exactly how much of the bound variable is consumed when the function is applied. r is the per-variable demand, not a whole-context scalar.

Concrete Instantiation — Dataflow (Precise)

Same carrier as flat (ℕ) but now as a per-variable vector:

Carrier per variable: ℕ ∪ {∞} ⊕ = max (pick larger requirement when branches join) ⊗ = + (sequential: prev∘prev adds requirements) 0 = 0 (not needed) 1 = 0 (current value only — cost-free access) Example: ⊢ x + prev y @ ⟨0, 1⟩ : Num x needs 0 past values; y needs 1 past value. Structural recovers the precision flat loses.

Concrete Instantiation — Variable Liveness

Carrier: 𝔹 = {0, 1} (Boolean semiring) ⊕ = ∨ (OR: variable is live in either branch) ⊗ = ∧ (AND: variable live in both sequential parts) 0 = false (dead) 1 = true (live) Example: ⊢ if b then x else y @ ⟨1, 1, 1⟩ : τ b, x, y all live; any unused variable gets 0.

Concrete Instantiation — Linear Types / Resource Usage

Carrier: ℕ (use-count semiring) ⊕ = + (usage from each branch adds up) ⊗ = × (sequential uses multiply) 0 = 0 (never used) 1 = 1 (used once = linear) Example: λx. x + x @ x:2 (x used twice — not linear)

§5

The Indexed Comonad — Categorical Semantics

"We present a unified calculus for tracking context dependence in functional languages together with a categorical semantics based on indexed comonads." — Petricek, Orchard, Mycroft exact [ICALP 2013]
"indexed comonads are the right foundation for constructing context-aware languages and type systems and that following an approach akin to monads can lead to a widespread use." — Petricek, Orchard, Mycroft exact [ICALP 2013]

An indexed comonad (called a graded comonad in later literature) parameterises a comonad by an element of the index algebra. Each value of the annotation r gives a distinct functor:

General shape of an indexed/graded comonad: D : I → (C → C) indexed family of endofunctors ε : D_1(A) → A counit (1 = identity annotation) δ : D_r⊗s(A) → D_r(D_s(A)) comultiplication (graded by ⊗) Subject to graded analogues of comonad laws: D_1 ≅ Id (counit law) D_r ∘ D_s ≅ D_{r⊗s} (cofusion law)

Flat Coeffect Comonad

The index set I is the semilattice (L, ⊔). The functor D_r wraps a value together with the entire context annotated at level r reconstructed:

Implicit parameters instance: D_S(A) = A × (Names →_S Val) value paired with partial env over set S ε (v, env) = v extract value, discard env δ (v, env) = ((v, env|_s), env|_r) split env by r⊗s = r∪s Dataflow (flat) instance: D_n(A) = List_n(A) non-empty list of length ≥ n+1 ε (a₀ ∷ _) = a₀ counit = extract current value δ = cobind (split history by sub-lengths)

Structural Coeffect Comonad

The index set I is the semiring (R, ⊕, ⊗, 0, 1); the comonad now tracks per-variable context. The index is a context (vector of semiring elements), not a single scalar reconstructed:

Structural comonad index = coeffect-annotated context Γ: D_Γ(A) where Γ = (x₁:τ₁@r₁, …, xₙ:τₙ@rₙ) ε : D_{Γ@1}(A) → A (all annotations are 1 = "used once") δ : D_{Γ@r⊗s}(A) → D_{Γ@r}(D_{Γ@s}(A)) Dataflow structural instance: D_{⟨n₁,…,nₖ⟩}(A) = A × DF_n₁(X₁) × … × DF_nₖ(Xₖ) each variable xᵢ carries its own history of length nᵢ The "structural system enjoys desirable syntactic properties" including subject reduction; the flat system does not in general.
"the structural system enjoys desirable syntactic properties" — Petricek, Orchard, Mycroft exact [ICFP 2014]

Concrete Comonad Objects from the Interactive Tutorial

From tomasp.net/coeffects (confirmed, high fidelity): Implicit Parameters comonad (flat): IP<A> = { value: A; lookup: Name → Value } counit ip = ip.value cobind f = λip. f { value = ip.value; lookup = ip.lookup } Dataflow comonad (flat or structural): DF<A> = NonEmptyList A (head = current, tail = history) counit (a ∷ _) = a cobind f xs = map (λi. f (drop i xs)) (indices xs)

§6

Which Analyses Are Flat vs Structural — Summary

The ICALP 2013 paper uses all three examples below to motivate the framework. The ICFP 2014 paper then shows that the flat treatment loses precision and develops the structural calculus to recover it:

Analysis Flat (ICALP 2013) Structural (ICFP 2014)
Implicit parameters Set of required names; ∪ = join. Tracks which parameters a computation depends on globally. Per-variable: which variables depend on which implicit bindings. Finer-grained dependency.
Dataflow / caching Single natural number = max past values needed by any variable. Whole-context annotation. Vector ⟨n₁,…,nₖ⟩: exactly how many past values each variable needs.
Liveness analysis Global set of live variables as the annotation r. Per-variable boolean; dead variables get 0, live get 1.
Linear types Not naturally expressible in flat. Per-variable use count in ℕ semiring; 1 = linear, 0 = unrestricted-but-unused.
Context-sensitivity / rebindable resources Set of required resource names as flat annotation (e.g., {LOCAL_FILE_SYSTEM}). Per-variable resource demands. Relevant for platform heterogeneity.

§7

Confidence Notes and Caveats

Exact quotes confirmed from primary source pages (tomasp.net, d3s.mff.cuni.cz): §§ 1, 2, 5, and the ICFP 2014 quote in §3. The typing rules and comonad formulas in §§ 3 and 5 are reconstructed from three or more corroborating secondary descriptions of the papers; the papers' PDF content was not machine-readable during fetching. The symbolic notation (⊕, ⊗, D_r, δ, ε) is consistent across all sources consulted. The concrete comonad objects (IP<A>, DF<A>) are confirmed from the tomasp.net/coeffects interactive tutorial.

One claim in search summaries — "most subsequent literature focuses on structural coeffects for which there is a clear algebraic description in terms of semirings" — appeared in near-identical form in three independent secondary source summaries; treated as reliable paraphrase of the ICFP 2014 paper.

The distinction between ICALP 2013 as the flat/primary treatment and ICFP 2014 as the generalized/structural treatment is confirmed by both the thesis overview (tomasp.net/academic/theses/coeffects/) and the D3S publication pages for both papers.
